# MerchantPay Lite — Customer Payment Journey Frontend Implementation Plan

## Goal Description
Implement the complete Customer Payment Journey for MerchantPay Lite using Next.js (App Router), React, TypeScript, and the existing design system. The user journey follows the three core BRD phases:
1. **Checkout Initiation**: View payment request details, merchant identity, amount, currency, and select payment method.
2. **Payment Fulfillment**: Input authorization details for supported methods (Card, Bank Transfer, USSD) with input masking and validation without storing sensitive cardholder details.
3. **Verification & Confirmation**: Display immediate feedback covering all supported states (`SUCCESSFUL`, `FAILED`, `PENDING`, `EXPIRED`, and `PROCESSING`) with safe retry handling.

The implementation strictly preserves the existing design language (colors, `Public Sans` and `IBM Plex Mono` typography, "P" brand mark, radii, buttons, and alert patterns) from `paymentapp-main.zip` and does not break existing merchant functionality (`index.html`, `register.html`, `merchant-dashboard.html`, `email-verification.html`).

## User Review Required

> [!IMPORTANT]
> **Backend Integration Status: BACKEND API REQUIRED**
> Inspection of the repository and `assets/js/config.js` shows that the existing ASP.NET backend only provides merchant-facing endpoints (`/Home/Login`, `/Merchants/Register`, `/Payments/Dashboard`, `/Payments/Create`). Customer-facing checkout endpoints (`GET /Payments/Checkout/{reference}`, `POST /Payments/Charge`, `GET /Payments/Status/{reference}`) **do not yet exist** in the backend.
> 
> As mandated by Rule 8 of the prompt:
> - We will **NOT** invent endpoints or fake production payment processing.
> - We will create a strongly-typed API service layer `lib/api/checkout-service.ts` that isolates this boundary and marks the missing endpoints as `BACKEND API REQUIRED`.
> - For UI development, validation, and browser verification across all payment states, we provide an isolated fixture provider (`lib/api/dev-fixtures.ts`) active only in development/demo mode (e.g. when testing specific state scenarios like `?status=success`, `ref-success`, `ref-fail`, `ref-pending`, `ref-expired`).
> - We will document all required API contracts in `docs/customer-checkout-api-dependencies.md`.

> [!NOTE]
> **Existing Merchant Pages Preservation**
> The existing merchant static HTML files (`index.html`, `register.html`, `email-verification.html`, `merchant-dashboard.html`) and their associated assets (`assets/css/*`, `assets/js/*`) will remain intact. They will also be served via Next.js `public/` directory so that navigating to `/index.html`, `/register.html`, etc. continues to work identically.

### Data Types & API Layer

#### [NEW] [types/checkout.ts](file:///home/gamp/projects/THxZV/paymentapp/types/checkout.ts)
- Types for:
  - `PaymentStatus`: `'INITIATED' | 'PROCESSING' | 'SUCCESSFUL' | 'FAILED' | 'PENDING' | 'EXPIRED' | 'NOT_FOUND'`
  - `PaymentMethodType`: `'card' | 'bank_transfer' | 'ussd'`
  - `CheckoutSession`: Session payload (merchant, amount, currency, reference, expiresAt, narration)
  - `PaymentSubmission`: Card, Bank Transfer, USSD submission payloads
  - `PaymentResult`: Transaction status response

#### [NEW] [lib/api/checkout-service.ts](file:///home/gamp/projects/THxZV/paymentapp/lib/api/checkout-service.ts)
- API service contract:
  - `getCheckoutSession(reference)`
  - `submitPayment(reference, payload)`
  - `getPaymentStatus(reference)`
- Integrates with backend endpoint `API_CONFIG.BASE_URL` if configured.
- Explicitly flags customer checkout endpoints as `BACKEND API REQUIRED` when running against the ASP.NET backend.
- Provides seamless dev fixture integration when in testing/demo mode without polluting production logic.

#### [NEW] [lib/api/dev-fixtures.ts](file:///home/gamp/projects/THxZV/paymentapp/lib/api/dev-fixtures.ts)

## Verification Plan

### Automated Verification
1. **Linting**:
   ```bash
   npm run lint
   ```
2. **TypeScript Compilation**:
   ```bash
   npm run typecheck
   ```
3. **Production Build**:
   ```bash
   npm run build
   ```

### Browser / Manual Verification
1. **Successful Payment Flow**:
   - Navigate to `/checkout/MP-DEMO-SUCCESS` (or with demo toggle).
   - Verify Initiation: Merchant name, `₦10,000.00`, reference in `IBM Plex Mono`.
   - Select Card, fill form, submit.
   - Verify Processing state spinner.
   - Verify Success confirmation screen with all transaction details.
2. **Failed Payment & Retry Flow**:
   - Navigate to `/checkout/MP-DEMO-FAIL`.
   - Select Card or USSD, submit.
   - Verify safe error notice.
   - Click "Try again", verify it returns to details without losing session.
   - Click "Choose another payment method", switch to Bank Transfer.
3. **Pending Payment Flow**:
   - Navigate to `/checkout/MP-DEMO-PENDING`.
   - Select Bank Transfer, click "I've sent the money".
   - Verify Pending screen with amber status pill.
4. **Expired Payment Flow**:
   - Navigate to `/checkout/MP-DEMO-EXPIRED`.
   - Verify Expired screen notice.
5. **Existing Merchant Application Verification**:
   - Verify `index.html` (Login), `register.html`, `email-verification.html`, and `merchant-dashboard.html` still render and behave properly.
6. **Mobile Responsiveness & Accessibility**:
   - Test viewport widths (375px, 414px, 768px, 1024px).
   - Check contrast, ARIA labels, keyboard focus rings (`var(--accent)`).
